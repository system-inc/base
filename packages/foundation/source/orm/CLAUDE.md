# orm/ — Drizzle ORM

The framework's **ORM** — the sole ORM path. You define entities with decorators; this subsystem turns them into a portable schema model, builds real [Drizzle](https://orm.drizzle.team) tables from it, executes through a per-backend adapter, and hydrates raw rows back into entity instances. ~150 files; this is the one folder-level doc for the whole subsystem.

## How it's consumed

Declare an entity, register it in a module's `orm.entities`, then inject a repository:

```ts
@OrmTable('account')
export class Account extends OrmTrackingEntity {
  @OrmPrimaryAutoColumn('uuid') declare id: string
  @OrmColumn({ kind: 'varchar', length: 255 }) declare email: string
  @OrmColumn({ kind: 'varchar', length: 255 }, { nullable: true }) declare name: string | null
}

// in a service
constructor(@InjectRepository(Account) private accounts: OrmRepository<Account>) {}
```

`@InjectRepository(Entity, DatabaseBinding?)` and `@InjectDatabase(DatabaseBinding?)` resolve from the DI container; the optional `DatabaseBinding` selects a named data context explicitly (an explicit binding always wins). With **no** binding, resolution is **module-aware** (see below).

### Module-aware database resolution

A token-less `@InjectRepository(Entity)` / `@InjectDatabase()` resolves to **the database the injecting class's declared module resolves to**. Precedence at every injection site:

1. an explicit `DatabaseBinding`/key passed to the decorator — always wins;
2. else the class's **declared module membership** — a `BaseModuleKey` passed to its injectable-family decorator (`@Injectable(FileStorageModuleKey)`, `@WorkerScoped(FileStorageModuleKey)`, `@ContainerScoped(...)`, …). Membership is inherited by subclasses and a class belongs to exactly one module (declaring two throws at class definition);
3. else the **default** database — a deliberate, uniform contract: an undeclared class resolves identically in every worker, regardless of how many databases it configures. (A worker whose only database has a non-default name resolves to that one.)

**Registration never routes injections.** Listing a class in a `ModuleSettings` slot is _discovery and exposure_ — it puts the class in the bundle and in the worker's dispatch surface — not attribution. A class in a module whose database isn't the default **must** declare its membership (or take explicit bindings); boot validation enforces this: the token-less inject decorators mark their class at definition time, and `BaseAppManifest.validate()` rejects a non-default-database module's registered class that carries token-less injections without a declared key. Two more boot/injection checks keep declarations honest: a declared key naming a module absent from the worker throws at injection; a registered class whose declared module resolves to a **different** database than its registering module throws at boot, as does an undeclared class registered by two modules resolving to different databases (contradictory attribution). A misrouted default is additionally caught by the runtime entity guard (`requireOwnEntity`) with a clear error, not a silent query against a missing table.

A module's database is its `settings.orm.databaseName`, as overridden by the worker's `database` registration modifier (per deployment — see [module/](../module/CLAUDE.md)); declared membership resolves through that, so it stays portable across workers. This is what lets a module be **reused across workers that store its data in different physical databases** without per-worker code changes: the module's classes declare their home once (`@Injectable(FileStorageModuleKey)`), and each worker decides the destination via one registration line (`SomeModule.with({ database: 'connected', externalSchema: true })`). It's resolved **once at injection** (not per operation), so the returned `OrmDatabase` is a real, named context — `db.name` is honest and `execute()`/`transaction()` go there. The mechanism: a membership store written by the class decorators (`dependency-injection/ModuleMembership.ts`) plus a module→database map and a validation-only class→registration index built while the manifest flattens (`BaseAppManifest`), consulted by `BaseConfiguration.getDatabaseNameForClass` via `OrmDatabaseFactory.getDatabase(token, requestingClass)`; the inject decorators capture the decorated class (the constructor `target`) and forward it to the transform.

**Helpers declare their home — and need no registration.** Because every class participating in constructor injection already carries an injectable-family decorator, module membership is declared exactly where injection capability is declared. A helper injected by class token is imported by its consumers, so it's in the bundle without any settings entry: stamp it with `@Injectable(FileStorageModuleKey)` and it routes correctly. (Dispatched classes do appear in `services` — but that lists existence, not membership; membership is always the key on the class or, for entities, the `orm` slot.)

**Shared helpers.** Resolution keys off the _injected class_, not the caller. A helper injected across many modules resolves **its own** declared module's database — the same for every caller, never caller-dependent (a worker/container-scoped instance is cached, so per-caller routing is neither possible nor attempted; that would require the per-module DI scope Base deliberately avoids). A helper that must act on the **caller's** database takes the `OrmDatabase`/`OrmRepository` as a parameter, which the calling service (whose own injection is already module-aware) passes in.

### Read-only views

To get a read-only repository or database, **annotate the injected parameter** as `OrmReadonlyRepository<T>` / `OrmReadonlyDatabase` — there is no separate injector. The full `OrmRepository`/`OrmDatabase` that `@InjectRepository`/`@InjectDatabase` resolve are structural supersets of the read-only interfaces, so the narrower annotation simply hides the write surface (`insert`/`update`/`delete`/`upsert`/`writeBatch`/`truncate`/…) at compile time, and `OrmReadonlyDatabase.getRepository` hands back an `OrmReadonlyRepository`:

```ts
constructor(
    @InjectRepository(Account) private accounts: OrmReadonlyRepository<Account>,
) {}
```

It's an **opt-in, compile-time** guardrail — a consumer that wants write-discipline on a binding it only reads (e.g. external/inherited schema it doesn't own) annotates it read-only; one that doesn't uses the full type. It is deliberately _not_ runtime enforcement: an explicit `as OrmRepository<T>` cast escapes it, which keeps an intentional write **visible** rather than mandating a service layer (Base doesn't dictate that architecture). The structural subtyping both ways is locked by `database/OrmReadonlyAssignability.test.ts`, so a return-type change on either side fails the build rather than silently making the annotation reject the injection.

Note the **`declare`** keyword on every decorated column property — it's mandatory (enforced by the `base/orm-column-requires-declare` lint rule). The reason is **dirty tracking**: `OrmTrackingEntity` (the base class) installs a getter/setter accessor for each column on the concrete class's **prototype**, once per class on first construction (per-instance installation was ~70% of a hydrated row's cost), so that assignments are recorded as changed fields (see below). `declare` makes the property type-only — nothing is emitted — so those accessors survive. Without it, the emitted class-field initializer would, under `useDefineForClassFields`, `[[Define]]` a plain data property on the instance that **shadows the tracking accessor**, silently breaking change tracking.

## The pipeline (how a query actually happens)

```
@Orm* decorators ──► metadata registry ──► schema builder ──► Drizzle tables
   (decorators/)      (metadata/)            (schema/)          (drizzle-orm)
                                                                      │
OrmRepository / OrmDatabase ──► OrmAdapter ──► driver ◄───────────────┘
   (database/, database/repository/)  (database/adapter/)
        │                                   │
   find/insert/update/delete/batch     execute / transaction / writeBatch
        │
   OrmEntityHydrator ──► entity instances (raw rows → OrmTrackingEntity, runs @OrmAfterLoad)
   (hydration/)
```

1. **Decorators** (`decorators/`) describe an entity: `@OrmTable`, `@OrmColumn`, `@OrmPrimaryKey` / `@OrmPrimaryAutoColumn`, `@OrmCreateDateColumn` / `@OrmUpdateDateColumn`, relations (`@OrmManyToOne`/`@OrmOneToMany`/`@OrmOneToOne`, `@OrmJoinColumn`), indexes/uniques (`@OrmColumnIndex`, `@OrmTableIndex`, `@OrmColumnUnique`, `@OrmTableUnique`, … — a table-index column may declare `{ column, prefixLength }` for MySQL prefix indexes, checked against InnoDB's 3072-byte key cap at generate time and ignored by SQLite), and lifecycle hooks (`@OrmBeforeInsert`/`@OrmAfterInsert`/`@OrmAfterLoad`/… for all of insert/update/delete + load). Each decorator both `mark()`s the class in the shared `DecoratorRegistry` (boot-time validation) and writes into the metadata registry.
2. **Metadata registry** (`metadata/OrmSchemaRegistry.ts`) — a module-level `Map<class, OrmTableMetadata>`. `OrmTableMetadata` is the **portable, Drizzle-independent** description: columns, relations, indexes, unique constraints, lifecycle listeners, and date columns. All the `Orm*Metadata` types live here.
3. **Schema builder** (`schema/`) — `OrmSchemaBuilder` (with dialect variants `OrmSchemaBuilderDrizzle`, `…DrizzleSQLite`, `…DrizzleMySql`) translates the metadata into actual Drizzle table objects using `drizzle-orm/sqlite-core` / `mysql-core` column builders and `relations()`. `OrmSchemaCheck`/`OrmSchemaHelpers` validate and classify columns. This is the seam that keeps entity definitions decoupled from Drizzle's builder API.
4. **Adapter** (`database/adapter/`) — `OrmAdapter` abstracts execution against a concrete backend: `execute` (raw driver result), `executeRows` (raw SELECT normalized to a plain row array — the dialect-independent way to consume raw queries; MySQL drivers resolve `{ rows }`, SQLite the array itself), `transaction`, `writeBatch`, and a `supportsInteractiveTransactions` flag. `OrmAdapterProvider` builds an adapter for a named database from `OrmSettings` + metadata. Implementations: `drizzle/sqlite/` (`D1Adapter`, `BetterSQLiteAdapter` + providers), `drizzle/mysql/` (`MySqlAdapter`, `PlanetScaleProvider`), and `OrmDurableAdapter` (Durable Object SQLite). `OrmDrizzleDurableMigrationRunner` runs migrations inside a Durable Object.
5. **Database + repository API** (`database/`) — `OrmDatabase` is the high-level data context (find / insert / update / delete / batch / time-series) over an adapter; `OrmDurableDatabase` and `OrmReadonlyDatabase` are variants; `OrmDatabaseFactory` creates them per named config; `database/internal/OrmDatabaseImpl` is the impl. `database/repository/OrmRepository` is the per-entity repository surface. `database/transaction/` holds `OrmTransaction` and its callback/result types.
6. **Find options + filters** — `interfaces/find/` (`OrmFindOptions`, `…Many`, `…Where`, `OrmMappedJoin`, `OrmTimeSeriesOptions`) and `filters/` (a composable filter algebra: `OrmEqualsFilter`, `OrmAndFilter`/`OrmOrFilter`/`OrmNotFilter`, `OrmBetweenFilter`, `OrmLikeFilter`, `OrmInArrayFilter`, `OrmIsNullFilter`/`OrmExistsFilter`, and `Not*` variants). `interfaces/result/` holds typed results (`OrmInsertResult`, `OrmUpdateResult`, `OrmDeleteResult`, `OrmBatchResult`, `OrmTimeSeriesResult`). Pagination lives at the top level: `OrmPaginatedFind`, `OrmPaginationInput`, `OrmColumnFilter`.
7. **Hydration** (`hydration/OrmEntityHydrator`) — converts raw Drizzle rows into entity instances (`OrmTrackingEntity` subclasses), runs `@OrmAfterLoad` listeners, and controls relation depth (`maxDepth`, `raw`).

## Design choices worth knowing

- **Entities track their own changes.** `OrmTrackingEntity` is the base for all entities (`OrmBaseEntity` adds a uuid `id` + `createdAt`; `OrmMutableBaseEntity` adds `updatedAt`). Each column property is a prototype getter/setter (value stashed in `__<field>` on the instance; installed once per class, on first construction); the setter compares old vs new and calls `markChanged`, so `getChangedFields()` returns just the dirty columns — enabling minimal partial updates. `@OrmAfterLoad`/`@OrmAfterInsert`/`@OrmAfterUpdate` reset the dirty set. It also provides `from(data)`, `clone()`, and a cycle-safe `toJSON()`. This is why decorated columns must use `declare` (see _How it's consumed_).
- **Which field set each write persists (the contract).** `insert` sends **every set column** (`undefined` columns are omitted, so database defaults still apply) — an insert has no baseline to delta against, and driving it from the dirty set silently stored empty rows for clean-but-populated entities (`clone()`d or re-inserted hydrated instances). `update` (entity-based) sends **only `getChangedFields()`** — the dirty-tracking optimization, and the reason the accessors exist. `upsert` uses insert-shaped values (all set columns, so the insert half is complete) with an update-shaped conflict SET that **excludes create-date columns** (`createdAt` is immutable across upserts). Entity-identified writes require the **complete** primary key — a partial composite key throws instead of widening the WHERE to sibling rows.
- **Portable metadata model, then Drizzle.** Entities never touch Drizzle's table-builder API directly; they describe themselves via decorators → `OrmTableMetadata`, and the schema builder emits Drizzle. Swapping or extending dialects happens in `schema/` + `database/adapter/`, not in entity code.
- **Backend portability around transactions.** `OrmAdapter.supportsInteractiveTransactions` is `false` for D1 (batch-only via `writeBatch`); portable code should prefer `writeBatch` and only reach for `transaction(...)` when the flag is true.
- **`OrmAdapterType` is just `'drizzle'`.** The backend is a (dialect, driver) pair (`OrmDatabaseType` in `database/adapter/OrmDatabaseType.ts`): SQLite × {`d1`, `durable`, `better-sqlite`} and MySQL × {`planetscale`}. Postgres is deliberately absent until a driver is actually wired — the union states what works, not the roadmap.
- **Lint enforces decorator/type parity.** `base-lint` rules (`orm-column-nullable-parity`, `orm-column-requires-declare`, `relation-must-be-optional`) keep column nullability, the `declare` keyword, and relation optionality in sync with the TypeScript types — relations must include `undefined` because they aren't eagerly hydrated.
- **Migrations are CLI-driven.** `base orm` (drizzle-kit under the hood) generates/runs SQL migrations; `OrmDrizzleDurableMigrationRunner` handles the Durable Object case at runtime. See the [cli](../../../cli/CLAUDE.md) doc.
- **Owned vs external entities (shared databases).** A worker _owns_ (migrates) the entities in its `orm.<db>.entities` and any module registered normally. Entities a worker only _uses_ land in `externalEntities` (manifest `orm[db].externalEntities`, `OrmConfiguration.externalEntities`), from four sources: a module registered with `externalSchema: true`, a module's own `orm.externalEntities` (tables it self-declares it needs to query — reference another module's exported `*Schema` entity array; this is how a module stays self-describing about its schema deps, distinct from `uses` which is a module dependency), entities listed directly in the worker's `orm.<db>.externalEntities`, or those pulled in by a database's `inheritSchema` source. The runtime query schema is built from **owned ∪ external** (so queries/relations work), but migration generation and the `schema:sync` table scope use **owned only**. This is what lets two workers share one database without their migrations colliding: each table has exactly one owner; everyone else marks it external. (The same entity _class_ may be owned by more than one database within a single worker — those are distinct physical tables in distinct databases, which is fine; "one owner" is per table/physical-database — and `check --all-workers` / `deploy --all-workers` enforce it: the CLI compares ownership claims across workers by physical database identity (D1 `database_id`, PlanetScale host+database) and fails when two workers own the same table.) Within one database the schema is keyed by table name, so the **same table registered more than once** (owned + an external reference, or declared external by several modules) is **idempotent** — `OrmDatabaseImpl.allEntities` dedups by class, and the drizzle build overwrites the same name with an equivalent table. At runtime `OrmDatabaseImpl` guards every entity-typed call (`requireOwnEntity`): an entity not in that database's owned ∪ external set throws a clear error instead of an opaque driver "no such table" — catching a mismatched explicit binding or a misrouted module early. See [module/](../module/CLAUDE.md) registration modifiers and **module-aware database resolution** above.
- **Mapped joins keep hot paths at one round trip.** `find`/`findOne` accept `joins:` (`OrmMappedJoin`) — ad-hoc joins for related rows that are _not_ declared relations: composite predicates (`{ accountId: parentColumn('accountId'), profileId: parentColumn('profileId') }`), filtered loads (`status: Active`), nested declared relations, and nested joins. Each compiles into a correlated JSON-aggregation subquery (`json_arrayagg` on MySQL, `json_group_array` on SQLite) inside the _same_ SQL statement as the find, and the hydrator parses the JSON back into entity instances — so a find with declared relations plus any number of mapped joins is still a single database round trip. This matters because PlanetScale is an HTTP round trip per query; account's session loader uses it to load the whole session graph in one statement on every authenticated request. Limits: scalar filters only in a join's `where` (no `and`/`or`/`not`), no ordering inside a `many` join, `bytes` columns are skipped.
- **Mode-bearing columns declare their `mode` explicitly.** `bigint` (`'number' | 'bigint'`), `decimal` (`'string' | 'number' | 'bigint'`), and `datetime` (`'date' | 'string'`) all require `mode` — type-enforced, with a schema-build-time throw (`requireColumnMode`) backstopping JS callers. The mode encodes a per-column fact the framework can't know: whether the value can exceed 2^53 (`bigint`), whether a lossy float64 representation is acceptable for a type chosen _for exactness_ (`decimal` — `'string'` for money-like values, `'number'` for inherently approximate measurements), and how timestamps surface (`datetime`). A default would be a silent guess between materially different correct answers, so there isn't one.
- **One primary key, declared once.** Multiple `primaryKey: true` columns never merge into a composite — column order defines the backing index, so the framework won't guess it. Any conflicting declaration throws (at class-definition time, or at metadata merge for inheritance): a second flagged column, `@OrmPrimaryKey` on top of a flagged column or `@OrmPrimaryAutoColumn`, or a subclass key fighting an inherited one. Compound keys are declared exactly once with class-level `@OrmPrimaryKey([...])`, ordered by the hot lookup path; the one sanctioned overlap is a subclass **widening** an inherited key into a composite that still contains it (e.g. `@OrmPrimaryKey(['id', 'tenantId'])` on an `OrmBaseEntity` subclass).
- **No implicit many-to-many.** There is deliberately no `@OrmManyToMany`/`@OrmJoinTable` — junction tables almost always grow their own columns, need direct writes, and implicit m2m hides both. Model the junction as an explicit entity: an `@OrmTable` with a composite `@OrmPrimaryKey` and ordinary `@OrmManyToOne` relations to each side (see `UserNetworkUserDevice` in access-log or `AccountProfile` in account). Traverse it either by nesting relations through the junction (`relations: { accountProfiles: { profile: true } }`, then map to flatten) or with a two-step junction find + `inArray()` query; write memberships with plain `insert`/`deleteWhere` on the junction entity.
