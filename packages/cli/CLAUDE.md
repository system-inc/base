# @system-inc/base-cli

The `base` command-line tool: scaffolds, builds, bundles, runs, and deploys Base-powered Cloudflare Workers, and drives ORM migrations and GraphQL schema generation. Depends on all three runtime packages (`foundation`, `client`, `common`).

## Purpose

A worker is a directory with a `settings.ts` exporting a `BaseSettings` instance. The CLI discovers those workers, loads their settings at runtime (via `ts-node`), and orchestrates everything around them — bundling with esbuild, running/deploying via `wrangler`, generating GraphQL SDL from `type-graphql` decorators, and managing Drizzle migrations. It also scaffolds new workspaces and workers from templates.

## Entry point + how it runs

- Source entry: `source/base-cli.ts` → built to `dist/base-cli.js`, exposed as the `base` bin.
- From the repo: `npm run base -- <command>` (e.g. `npm run base -- check --all-workers`).
- Command framework: **yargs**. Global options `--worker/-w`, `--environment/-e`, `--workers-folder`.

### Worker resolution

`workersFolder` is resolved in priority order: `--workers-folder` flag → inferred from CWD (if CWD is a worker) → root `package.json` `base.workersFolder` (this repo points it at `./examples`) → `./workers/` → CWD. Single-worker commands act on the resolved/`-w` worker; `--all-workers` fans out to every directory containing `settings.ts`.

The same `package.json` `"base"` block can declare `persistTo` — a workspace-shared root for wrangler's local state, passed as `--persist-to` to `develop`, `orm migration:run --local`, `orm db:reset`, and `orm db:studio --local` (each also takes a `--persist-to` flag that wins). Miniflare keys local D1 state by `database_id`, so workers binding the same database then share one local sqlite — mirroring the shared remote database — instead of each worker holding a private copy under its own `.wrangler/`. Scaffolded workspaces declare `persistTo: "./.wrangler/state"` by default.

## Design choices

- **`settings.ts` is the source of truth.** Commands load a worker's `BaseSettings` at runtime to discover modules and ORM bindings — the CLI reflects the same app model `foundation` runs.
- **Template scaffolding** (`source/scaffold/CopyTemplate.ts`, `templates/`). Template files carry a `.template` suffix that is stripped on copy (`package.json.template` → `package.json`); dotfiles are de-fanged for npm packaging (`gitignore.template` → `.gitignore`). `{{key}}` placeholders are substituted in names and contents. Two trees: `templates/workspace/` (monorepo root: package.json, jest, GitHub workflows, VSCode config) and `templates/worker/` (single worker: `index.ts`, `settings.ts`, `wrangler.toml`, test + service examples).
- **Wrangler + TOML.** `source/cloudflare/Wrangler.ts` wraps `wrangler dev/deploy/tail`; `source/toml/` + `source/project/WranglerToml.ts` parse `wrangler.toml` and layered env (`env.toml`, `test.env.toml`) with `smol-toml`.
- **Local vs remote D1.** drizzle-kit's `d1-http` driver only speaks to the Cloudflare API, so drizzle-driven commands hit the REMOTE database for the resolved environment. Local D1 (wrangler's sqlite under `persistTo` / `.wrangler/state`) is reached differently per command: `migration:run --local` delegates to `wrangler d1 migrations apply --local`; `db:studio --local` maps the binding's `database_id` to miniflare's on-disk filename (`source/cloudflare/MiniflareState.ts`) and runs studio against that file via a generated `drizzle.local.config.ts` (plain `sqlite` dialect, path passed through `BASE_DRIZZLE_CREDENTIALS`). Remote studio prints a REMOTE warning.
- **Drizzle migration gating.** `source/orm/drizzle/` drives `drizzle-kit` for introspect/diff/generate, writes per-database `.sql` migrations, and tracks release state (`release.ts`); non-dev deploys are blocked while unreleased migrations exist. `.sql` files are registered as raw imports in `base-cli.ts`. The generated `drizzle.config.ts` sets a **per-worker migrations table** (`migrations.table = __drizzle_migrations_<worker>`, `drizzleMigrationsTableName`) so workers sharing one database keep independent migration histories — drizzle decides "applied?" from the single latest `created_at` in that table, so a shared default table would let one worker's rows silently skip another's migrations. The wrangler `d1_databases` entry must declare the same table in `migrations_table` (and drizzle's output folder in `migrations_dir`) — that's what `wrangler d1 migrations apply --local` tracks against — and `base check` fails a drizzle D1 binding whose worker owns tables in the database when either field is absent or disagrees (`CheckWorker.checkWranglerConfiguration`).
- **Workspace vs worker model.** A _workspace_ is the monorepo root (shared config + many workers); a _worker_ is a subdir with `settings.ts`. Most commands default to one worker; `--all-workers` enumerates them.
- **Why `ts-node` (not tsx or Node's native TS loader).** Looks legacy at a glance; it isn't. Our decorator-driven frameworks — `tsyringe` (DI), the ORM (`@Orm*` entities/columns), and `type-graphql` (GraphQL schemas) — all depend on `experimentalDecorators` + `emitDecoratorMetadata` producing reflection metadata (`design:type`, `design:paramtypes`, `design:returntype`) that matches `tsc`'s output _exactly_. Generics, aliased imports, and circular type refs all have to resolve through the full type checker. esbuild-based loaders (tsx, Node 22's experimental TS) do a faster lexical pass that diverges on these edge cases; the resulting metadata mismatches surface as silent DI/ORM/schema bugs rather than build errors. ts-node uses real `tsc` under the hood, so the metadata is identical to what these frameworks were authored against. The programmatic `require('ts-node').register({...})` in `base-cli.ts` also lets us install the loader mid-process before dynamically importing the worker entry, which tsx's CLI-first model doesn't cleanly support. Revisit when: (1) we move to TC39 stage-3 decorators and the affected libs adopt `Symbol.metadata`, or (2) esbuild's `emitDecoratorMetadata` is independently validated against our decorator usage end-to-end.

## Folder map (`source/`)

`commands/` (yargs command modules; subgroups `deploy/`, `graphql/`, `orm/`, `workspace/`) · `project/` (worker discovery `BaseWorkerProject`, env + wrangler config resolution) · `cloudflare/` (wrangler wrapper) · `orm/drizzle/` (credential/schema loading, migration release tracking) · `environment/` (env-var layering) · `scaffold/` (template copy + substitution) · `modules/` (module/test discovery) · `startup/` (preload hooks, reflect-metadata) · `toml/` (TOML wrapper) · `common/` (arg parsing, process exec, readline). Package-root `templates/` (scaffold sources) and `integration/` (end-to-end CLI tests).

## Testing

**CLI behavior is tested by spawning the built bin, never by running the CLI in Jest's VM.** The VM doesn't replicate the real runtime — ts-node registration, cwd-sensitive module resolution, the bundled `dist/` layout, ESM/CJS boundaries — so importing command/runtime code into a unit test gives false passes and false failures (e.g. the `__dirname`-based template resolution, or cwd-relative ts-node `moduleTypes`, behave differently in-VM than in the real bin).

- **`integration/*.cli-integration.test.ts`** — the source of truth for CLI behavior. Each drives the CLI through `integration/internal/RunBase` (`spawnSync('node', ['dist/base-cli.js', …])`). A jest `globalSetup` (`jest.globalSetup.js`) builds the bin once before the run, so these never test stale `dist/`.
- **`source/**/_.test.ts`** — unit tests for **pure logic only** (schema-diff algorithms, validators, arg/platform parsing, path resolution, file I/O), using mocks or tmp-dir fixtures so they behave identically in-VM and in the bin. They must not import the ts-node bootstrap (`startup/_`) — enforced by a `no-restricted-imports`rule in the root`eslint.config.mjs`. If a unit test needs to load settings, run `Base`, or depends on the bundled layout, it belongs in `integration/`instead. Be wary of transitive imports pulling runtime-only deps (e.g. Prettier's dynamic`import()`) into the VM.

## Key dependencies

`yargs` (CLI) · `wrangler` (Cloudflare dev/deploy) · `drizzle-kit` (migrations) · `smol-toml` (TOML) · `ts-node` + `tsconfig-paths` (load `settings.ts`) · `chalk` (output) · `libsodium-wrappers` (keygen) · `@graphql-tools/utils` (SDL) · `reflect-metadata`. Peer deps: `drizzle-orm`, `type-graphql`, `graphql`.

## Relationship to other packages

Consumes `foundation` (`BaseSettings`, `Environment`/`Platform` enums, env vars) and `common` (crypto for keygen, config/types). Builds the workers under `examples/`. It is the operational front end to the framework `foundation` defines.
